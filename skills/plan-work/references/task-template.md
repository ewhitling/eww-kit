# Plan and task template

Use plain Markdown. Keep task IDs stable when revising a plan.
Each task must make sense when copied independently into a tracker description.
Write a short story about the change, not a checklist of planning parameters.
Omit empty sections and unsupported field values. Surface consequential unknowns
in the relevant prose rather than filling gaps with plausible details.

## Plan

# [Outcome or capability]

Explain who needs the outcome, what prevents it today, and what success looks like.
Use a concrete example. Include agreed boundaries, constraints, and open decisions
only where they affect the approach or sequencing.

Use a milestone table when it helps explain delivery order:

| Milestone | Demonstrable capability | Task IDs | Dependencies |
|---|---|---|---|

## Task [ID]: [Verb and concrete deliverable]

### Problem

Explain what is difficult today and for whom. Connect this problem to the plan's
outcome. Include essential context so the assignee does not need the interview.

### Goal

Describe what becomes possible, with a concrete example of the result.
State relevant exclusions and decision boundaries in prose, not mandatory fields.
Include dependencies or unresolved decisions here when they constrain the result.

### First step

Give the first useful action and the inputs needed to begin.
Build proportionate design review into this action before substantial execution:
what to bring, who reviews when confirmed, and what may proceed before approval.
If a prerequisite or reviewer is missing, explain what is blocked and how to resolve it.
Include an agreed investigation timebox or review exemption when applicable.
Keep implementation choices with the assignee inside the agreed boundaries.

### Done

Use concrete bullets describing observable results and acceptance evidence.
Each criterion must make clear what will be checked, the expected result, and the
evidence to submit. Combine these naturally rather than requiring a four-column table.
Include validation review and acceptance authority when confirmed. State a reviewer
gap if it prevents acceptance. Preserve an agreed exemption and its reason.
Include pause conditions and handoff requirements only where consequential.
Never describe planned checks as already passed.

## Tracker fields

Keep these outside the task description. Include only confirmed values:
assignee, state, milestone, priority, and subtasks.
Use the destination tracker's vocabulary when provided; otherwise keep values
platform-independent. Do not invent tracker states or duplicate metadata in prose.
Subtasks describe independently useful work, not every mechanical step.
Omit this section if there are no confirmed fields. Report assignment or readiness
gaps in the relevant task prose or plan close instead of inserting placeholder fields.

## Plan close

Briefly identify the first executable work, blocked work and its resolution path,
and remaining manager decisions. Mention review capacity only when it affects delivery.
Use plain language rather than adding a second set of status labels to every task.

## Calibration

An artifact existing is not necessarily evidence of success.
For a process, publishing the procedure is a deliverable, not acceptance evidence.
A participant completing a representative case and an agreed exception case can
provide evidence. Agree acceptable results rather than inventing thresholds.
For investigations, acceptance concerns traceable findings, not confirmation of the
preferred hypothesis. An inconclusive result can still satisfy the investigation.

Review and validation are part of First step and Done, not separate mandatory
administrative sections. Add detail where risk demands it, not to fill a template.
